# Web 产品生产流程

## 总原则

保持人的操作简单，把正式治理留在后台：

1. 先检查仓库、文档、环境和既有 Baseline，再提问。
2. 只向人询问无法发现且会改变目标、范围、验收、风险或授权的信息。
3. 把未填写的非必填项设为默认值；用户回复“默认”时直接采用推荐默认值并记录依据。
4. 对人使用通俗中文。除非用户要求审阅治理细节，不展示 Task Profile、Artifact Manifest、状态模型和规范代码。
5. 不推测批准人、授权范围、验收结果、事实证据或风险接受结论。
6. 不因任务较小删除控制目标；缩放实例数量、物理载体、内容深度和派生视图。
7. 相同事实只维护一份权威定义；其他文件引用或按需生成视图。

## 读取规范

先读 [references/spec-source-map.md](references/spec-source-map.md)，定位唯一的规范根目录和权威来源。

按当前任务只读相关规范：

- 始终应用公共术语、受控产物目录、P2 适用性决议和跨规范产物归属索引。
- 始终保持 C07-C12 的最小治理闭环；只读取当前阶段涉及的章节。
- 新产品、产品定义、需求、验收或设计变化分别读取 C01-C06 中被触发的规范。
- 仅在触发条件成立或为 Unknown 时读取并激活 E01-E05。
- 将 V6.2.1 标记为 Candidate/In Review/Proposed 时，只作为候选规则执行；不得声称其已批准或已建立正式 Baseline。

禁止在 Skill 内重新定义 137 个产物类型、状态模型、风险等级或国际标准映射。始终以规范仓库为唯一事实源。

## 接收最小输入

只要求用户提供一项必填内容：

```text
期望结果（对应原“需求描述”）：
- 任务类型：默认由 Agent 判断；可写新产品/新功能/优化/缺陷修复/工程变更/内容配置/迁移替代退役/生产处置
- 当前情况：默认由 Agent 检查现有材料
- 希望变成什么：【必填】
- 验收示例：默认由 Agent 提议，二次确认时由人确认
- 明确不做：默认无额外排除项
```

采用以下默认值，不要求用户改写：

- 目标产品、仓库、目录和环境：自动发现。
- 截止时间：无固定期限。
- 参考资料：使用当前可访问材料。
- 额外约束：无；已发现约束仍然生效。
- 敏感数据或合规要求：未声明；必须通过检查和追问确认，禁止据此判为不存在。
- 验收决策：由发起人在验收门禁时确认；这不等于预先认定其具有组织授权。
- 发布决策：仅在涉及发布时，发布前确认有权角色。

若用户已经给出更多信息，直接吸收，不要求按模板重填。

## 执行 Grill Me 多轮澄清

先检查、后提问，并遵循以下循环：

1. 每轮只问 3-5 个最能消除歧义的问题。
2. 问题使用业务语言，给出推荐默认答案；允许用户回复“全部默认”。
3. 每轮结束后等待用户回答，不在同一轮自行假定答案并继续。
4. 简单且低风险的任务至少完成一轮；复杂任务完成 2-5 轮。
5. 每轮更新“已确认、Agent 判断、仍待确认”，不重复已回答问题。
6. 当继续提问不会改变目标、范围、验收、关键约束或风险时停止。
7. 若出现 High/Critical、不可逆变化、生产发布、权限扩大、安全/隐私影响或风险接受，必须单独向有权人类确认。

第一轮优先澄清“为谁解决什么问题、希望出现什么行为、怎样算完成”。后续轮次再澄清边界、异常、数据、权限、兼容、发布和观察。

## 生成后台任务包

澄清后生成内部 Task Profile：

```text
Execution Scope =
Delivery Scenario
× Development Type
× Change Surfaces
× C02 Risk Level
× E01-E05 Extension Triggers
× Baseline Inheritance
× Normal/Emergency Mode
```

同时记录：

- 每项判断的事实依据；
- High、Medium 或 Low 置信度；
- 未决问题及其 Owner；
- 哪些结论来自用户确认，哪些来自 Agent 检查；
- 需要人类决定的门禁。

只使用 C02 的 `Low / Medium / High / Critical`，禁止创建任务挡位或第二套风险等级。Emergency 作为执行模式叠加，不作为开发类型。

## 生成产物清单

只列当前任务实际创建、修订、引用或已触发的产物。动作仅使用：

- `Create/Revise`
- `Reference`
- `Generate`
- `On Event`
- `N/A`

遵循以下规则：

1. 稳定且未变化的 Baseline 内容使用 `Reference`。
2. 查询、评审、审计或 Gate 需要的矩阵和报告使用 `Generate`。
3. Failure、Incident、Waiver、Risk Acceptance 等事实未发生时不创建空记录；发生后使用 `On Event`。
4. `N/A` 必须引用规则和范围；High/Critical 或扩展触发 Unknown 时禁止使用。
5. 允许多个独立 ID 共用一个结构化物理载体，但必须保持身份、字段、状态、关系和历史可区分。
6. VCM/DCM/BTM/RCR/ALR 从同一追踪关系生成；VER/VAE 保存权威证据，VDR 按 Run 汇总；CAS 保存通用变化，CCS 仅在代码变化时生成。

需要机器校验时，把后台任务包保存为 JSON，并运行：

```powershell
python scripts/validate_task_package.py <task-package.json>
```

## 按原流程推进

保持团队现有阶段名称、顺序、目录和文件习惯。仅在阶段背后执行规范路由：

1. **初次澄清**：检查材料并完成第一轮 Grill Me。
2. **二次确认**：给出通俗任务摘要、默认项、未决问题和验收示例；等待 `Proceed / Revise / Stop`。
3. **条件深化**：只在产品、新功能或需求修订时生成 PRD；只在 UI 变化且需要视觉决策时生成 HTML/PNG；只在设计或扩展规范触发时深化对应内容。
4. **计划**：形成唯一执行计划，列范围、步骤、验证、风险、回退和所需人类门禁。
5. **执行**：按批准范围修改，记录实际命令、变化、失败和证据，不扩大 Scope。
6. **验证与验收**：先由 Agent 运行可复核验证，再由人作验收决定；工具成功不等于验收通过。
7. **发布与观察**：仅在适用时执行；发布、回滚、风险接受和观察结论由有权角色决定。
8. **收尾**：记录 `Implemented / Deferred / Cancelled / Blocked / Superseded`、理由、责任人和影响；不声称“所有需求必须实现”。

继续使用以下载体：

- `*_需求澄清备案QA.md`：可选对话证据，不作为权威定义。
- `*_需求澄清备案FULL.md`：目标、范围、验收、决定和产物清单的唯一权威载体。
- `*_PRD.md`：仅用于产品、新功能和需求修订。
- `*_执行计划.md`：唯一执行计划；在同一文件追加 Run、验证和结果。
- HTML/PNG UI 效果：仅在 UI 变化且需要视觉决策时创建。

## 面向人的输出

每次只展示当前阶段需要的信息：

```text
当前结论
默认采用
需要你回答/决定
下一步
```

二次确认固定展示：

```text
要解决的问题
期望结果
本次会做
本次不做
如何验收
主要风险或未知
采用的默认项
请选择：Proceed / Revise / Stop
```

把正式规范代码、完整关系矩阵和未触发产物留在后台记录中。仅在用户要求审阅、Gate 需要或出现冲突时展开。

## 权限与事实边界

- 允许 Agent：发现上下文、分类、起草、维护追踪、生成派生视图、运行检查和报告缺口。
- 必须由人完成：目标和验收确认、范围取舍、批准、发布、例外、剩余风险接受和最终 Gate。
- 发现冲突、越权、关键证据不足或 Stop Condition 时立即停止受影响动作并升级。
- Emergency 可先执行恢复服务或控制损害所必需的动作，但必须补齐事实记录、变化、验证、风险、批准和事后评审。
