# 小红书审稿后台与全量投稿笔记输出 Profile

当任务满足以下任一条件时使用本 profile：

- 两端分别是“小红书审稿后台链路”和“全量投稿笔记链路”。
- 主键字段为 `稿件ID = 稿件id` 或语义等价字段。
- 用户要求“按之前的处理方式”“以链路命名版为规范”。
- 用户要求增量匹配，并排除前几轮已经匹配的稿件。

核心匹配仍由 `scripts/match_tabular_records.py` 完成；脚本生成通用结果后，再按本 profile 做确定性后处理。

## 1. 链路角色

| 角色 | 常见文件 | 主键 | 标题 | 作者 | 日期 |
|---|---|---|---|---|---|
| 审稿后台链路 | CSV 审稿结果 | `稿件ID` | `内容标题` | `作者昵称` | `发布时间` |
| 全量投稿笔记链路 | XLSX 投稿数据 | `稿件id` | `笔记标题` | `作者昵称` | `发布时间` |

主匹配使用 `id` 标准化。标题与作者只作为次级补充判断，使用 `text + text`，不得计入主键 inner join。

## 2. 增量匹配规则

1. 从每轮历史成品的 `匹配表_inner join` 提取唯一 `稿件id`。
2. 对各轮历史集合做交集检查，记录每轮数量、重叠数和累计唯一数量。
3. 从本轮审稿后台和全量投稿笔记两端同步剔除累计历史 ID。
4. 对剔除后的数据运行主键精确匹配。
5. 本轮匹配表、两张不匹配表均不得出现历史 ID。
6. 分析汇总必须记录：
   - 各轮历史匹配唯一 ID 数
   - 历史轮次之间的重叠数
   - 累计历史唯一 ID 数
   - 两端剔除历史记录数
   - 本轮两端参与记录数
   - 本轮匹配与双向不匹配数
   - 累计匹配唯一 ID 数
   - 本轮匹配与历史 ID 的重叠数，必须为 0

历史轮数可变，但汇总项目顺序不变。

## 3. 工作表顺序和名称

成品必须只有以下四个可见 sheet，并保持顺序：

1. `匹配表_inner join`
2. `不匹配详情_审稿后台`
3. `不匹配详情_全量投稿笔记`
4. `分析汇总`

成品中的 sheet 名、表头、状态、说明和结论不得出现“文件A”“文件B”“两个文件”。统一使用“审稿后台链路”“全量投稿笔记链路”“两个链路”。

## 4. 匹配表动态列规范

本节规定字段分组、优先级和命名方法，不规定固定列数。以本次输入的真实字段为准，不得为了复刻某个历史文件而添加空占位列。

### 4.1 列组顺序

按以下顺序动态编排；某组没有字段时直接跳过：

1. 业务派生结果列，例如 `最终审核结果`。仅在业务规则适用且依赖字段可识别时生成。
2. 核心身份列。小红书审稿场景默认优先级为 `加密uid`、`小红书号`、`稿件id`；仅保留实际存在或可可靠派生的字段。
3. 所有链接列。先放全量投稿笔记链路的链接，再放审稿后台链路的链接；各链路内部保持源字段顺序。
4. 全量投稿笔记链路的其余业务字段，保持源字段顺序。
5. 审稿后台链路的其余业务字段，保持源字段顺序。

若用户明确指定其他列组或顺序，以用户要求为最高优先级。列组内不得按字母重新排序。

链接列通过表头语义和数据共同识别，包括名称含 `链接`、`url`、`URL`、`uri`，或非空值稳定呈现为 `http://`、`https://` 的字段。不得只按历史字段清单识别。

### 4.2 命名规则

- 主键两端语义相同时，统一使用用户指定的业务名；本场景默认统一为 `稿件id`。
- 不使用 `文件A_`、`文件B_`、`左表_`、`右表_`等技术前缀。
- 名称唯一的源字段保留原名，不做无意义改写。
- 两端同名但含义不同或都需保留时，优先使用清晰的业务名；无法可靠改名时，先出现的字段保留原名，后出现的字段依次使用 `2`、`3` 后缀。
- 主键标准化值、连接辅助键和内部源行号不进入最终匹配表，除非用户要求保留审计字段。
- 每个应保留的源业务字段在成品中出现一次；不得静默丢列，也不得凭空补列。

历史文件中的 53 列布局只可作为输入字段恰好相同时的排列示例，不是跨任务的固定模板。

## 5. 最终审核结果公式

业务规则：

- `人工复核结果`非空：覆盖 `Agent审核结果`。
- `人工复核结果`为空：采用 `Agent审核结果`。
- 判断前后均执行 `TRIM`。

公式必须根据成品中的实际列位置生成，不得写死列字母。以第 2 行为例，逻辑模板为：

```excel
=IF(LEN(TRIM(<人工复核结果单元格>))>0,TRIM(<人工复核结果单元格>),TRIM(<Agent审核结果单元格>))
```

实现时先按表头定位两列，再换算当前列字母或使用可靠的结构化引用。公式填充至全部匹配行，不得将计算结果硬编码为静态文本。若依赖字段缺失或含义不明确，不生成伪结果，在分析汇总中明确记录。

分析汇总必须记录“人工复核覆盖记录数”和“采用Agent审核结果记录数”，两者之和等于 inner join 行数。

## 6. 不匹配详情结构

两张不匹配表均按以下顺序：

1. `来源行号`
2. `匹配状态`
3. 所有规范化主键组件
4. `次级字段补充匹配`
5. `补充匹配对方行号`
6. `补充匹配对方主键`
7. 该链路的全部源字段，保持原始字段顺序

状态固定为：

- 审稿后台：`仅审稿后台链路存在`
- 全量投稿笔记：`仅全量投稿笔记链路存在`

次级标题+作者匹配只标记“是”和对方信息，不移动到 inner join。

## 7. 行排序

- `匹配表_inner join`：按审稿后台源行号升序；重复主键时再按全量投稿笔记源行号升序。
- `不匹配详情_审稿后台`：按审稿后台来源行号升序。
- `不匹配详情_全量投稿笔记`：按投稿笔记来源行号升序。
- 无效主键记录保留在对应不匹配表，并维持源文件顺序。
- 不按稿件 ID 字符串重新排序，避免破坏源链路排查顺序。

## 8. 分析汇总章节

章节按以下顺序排列：

1. 标题和原始源文件路径
2. `主匹配配置`
3. `匹配概览`
4. `标准化审计`
5. `次级匹配与结论`
6. `增量过滤口径`，仅增量任务添加
7. `最终审核结果口径`

结论使用“两个链路部分重叠，互不包含”等链路表述。

章节顺序是默认规范；不适用的章节可省略，用户指定的专项分析插入结论之前。

## 9. Excel 视觉规范

### 通用

- 字体：`Microsoft YaHei`。
- 正文 9-10 pt，标题 16 pt。
- 隐藏网格线。
- 大表冻结首行和前置身份列；冻结位置按实际列组动态计算。
- 主键按文本保存。
- 链接和长文本换行，增加行高，不允许文字覆盖其他行。
- 使用浅色隔行底纹；不创建嵌套卡片或装饰性图形。

### 匹配表

- 表头底色：`#4F81BD`；白色加粗文字。
- 表格样式：`TableStyleMedium2`。
- 表头行高：34。
- 普通数据行高：30；存在链接或长文本并启用换行时为 46。
- 冻结：首行，并冻结到核心身份列组的最后一列；若无身份列，仅冻结首行。
- 列宽按字段角色设置，不按固定字母设置：
  - 业务结果/状态：14-20
  - 主键、UID、账号：18-30
  - 链接：40-50
  - 标题：28-36
  - 原因、备注、证据、标签等长文本：30-40
  - 日期时间：18-21
  - 数值、布尔值、源行号：10-16
  - 其他文本：16-24

`最终审核结果`条件格式：

| 值 | 填充色 | 字体色 |
|---|---|---|
| 优质稿 | `#C6EFCE` | `#006100` |
| 普通稿 | `#DDEBF7` | `#1F4E78` |
| 低质稿 | `#FFF2CC` | `#7F6000` |
| 无关稿 | `#F4CCCC` | `#9C0006` |
| 待人工审核 | `#E7E6E6` | `#404040` |

### 不匹配详情_审稿后台

- 表头底色：`#A80D3A`；白色加粗文字。
- 表头行高：34；数据行高：46。
- 冻结：首行和审计列组，位置按实际审计列数计算。
- 审计列按 12-30 设置；源字段按与匹配表相同的字段角色规则设置。

### 不匹配详情_全量投稿笔记

- 表头底色：`#C65911`；白色加粗文字。
- 表头行高：34；数据行高：46。
- 冻结：首行和审计列组，位置按实际审计列数计算。
- 审计列按 12-30 设置；源字段按与匹配表相同的字段角色规则设置。

### 分析汇总

- 标题底色：`#1F4E78`；白色 16 pt 加粗；行高 36。
- 源文件路径行底色：`#D9EAF7`；9 pt；行高 42。
- 常规章节标题底色：`#1F4E78`。
- 表头底色：`#37465A`。
- 增量过滤和审核口径章节底色：`#2E7D32`。
- 最终结论底色：`#FFF2CC`，字体 `#7F6000`。
- 列宽：A 30，B:C 33，D 40。
- 常规行高：24；长规则行高：38。
- 匹配率格式：`0.00%`。

列宽取上述区间内的动态值：根据表头和抽样数据的显示宽度计算，并限制在对应区间。中文字符按约 2 个英文字符宽度估算。不得因单个异常超长值把整列无限拉宽；超长内容使用换行。

## 10. 后处理步骤

1. 运行通用匹配脚本生成四表中间结果。
2. 读取匹配表中的两端源字段，按第 4 节识别字段角色并动态编排。
3. 删除通用匹配键、技术链路名和不需要的内部源行号等中间列。
4. 适用时按实际表头位置写入 `最终审核结果`公式并填充。
5. 重命名两张不匹配表和状态值。
6. 重写分析汇总中的链路名称、源文件路径、增量历史和审核口径。
7. 应用第 9 节全部样式。
8. 渲染四个 sheet，修复重叠、裁切、空白表头和异常列宽。
9. 导出唯一一份最终版，不交付中间结果。

## 11. 强制验证

交付前独立从原始文件和历史成品重新计算，不依赖中间报告：

- 历史各轮 ID 数、轮次交集和累计唯一数。
- 两端剔除后的增量集合。
- inner join、审稿后台独有、投稿笔记独有三个集合。
- 三个结果集合两两不相交。
- 历史 ID 在本轮三个结果 sheet 中出现次数为 0。
- 匹配表字段集合等于两端应保留业务字段的并集，加上适用的派生字段；无静默丢列、重复列或空占位列。
- 列组顺序符合第 4 节；所有链接列集中，投稿字段位于审稿字段之前。
- 同名字段的命名符合业务语义，且无“文件A/文件B”技术前缀。
- 每行审核公式按实际表头引用 `人工复核结果`和 `Agent审核结果`，缓存结果符合人工覆盖规则。
- 人工覆盖数 + Agent 采用数 = inner join 行数。
- 成品无“文件A”“文件B”“两个文件”。
- 无 Excel 公式错误。
- OOXML/ZIP 完整性通过。
- 四个 sheet 的可视化检查通过。
