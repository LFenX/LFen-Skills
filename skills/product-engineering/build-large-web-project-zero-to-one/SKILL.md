# 从 0 到 1 大型 Web 生产后台构建 SOP

## 用途与边界

当用户要从零或基于现有模板构建复杂 Web 管理后台，并希望按需求、产品设计、前后端执行计划和验收流程推进时使用本 Skill。

本 Skill 沉淀的是轻量、实战型交付流程，不替代正式治理审计。默认交付到验收环境；生产发布、上线后观察和回滚仅在用户明确要求时扩展。

与 `run-governed-product-workflow` 的分工：本 Skill 负责产品构建的实际协作顺序、文档产物、前后端绑定和返修闭环；需要团队治理载体、风险分级、正式发布证据或规范审计时，再使用后者。

## 核心术语

- **需求方**：提出业务问题并提供基础产品说明的人。
- **开发者**：负责需求澄清、PRD、产品包、代码实现和技术验收的人或 Coding Agent。
- **需求文档**：记录需求来源、原始表述及后续矫正的最终需求依据。
- **PRD**：把需求转化为产品形态的文档，说明产品意义、功能结构、角色、流程和交互。
- **产品包**：PRD、页面 SPEC/效果图、前后端执行计划及其索引的组合。
- **基线变更**：对原需求进行矫正、优化或新增；允许发生，但不能静默发生。

## 不可违背的规则

1. 需求文档保留每项需求的来源和演变，是最终需求依据；PRD 定义产品形态，不能反过来替代需求追溯。
2. 基础产品说明不要求一次穷尽所有细节；正式 PRD 不得留下未识别、未记录且会影响实现或验收的模糊项。
3. 开发者可以矫正、优化或新增需求，但必须说明原因，取得对应决定人/授权人的明确结论，并同步更新需求文档、PRD、产品包和受影响的前后端计划。
4. 产品包是正式开发前的工作基线。没有合适模板时，按用户指定的 UI 风格从零构建；有模板时先完成模板产品化配置，再开发业务功能。
5. 不得无依据自创功能、组件或交互。每个按钮、图标、行操作、菜单项和纯展示控件都要有唯一 `C-xxx`、需求或页面依据、明确入口和出口，并绑定角色/权限、数据/API/状态、前端任务、后端计划和验收场景；纯展示控件也必须标明数据来源和处理归属，不能留下死控件。G3/G4 前逐页核对，控件绑定覆盖率必须为 100%。
6. 前端发现新事实或改变基线时，先记录并同步文档和计划，再编码；后端阶段发现同类问题也遵守同一规则。
7. 原型验收与返修、前后端联调与修正、开发者验收与缺陷修复、联合验收与问题闭环都是循环，不以一次执行代替循环。
8. 验收按业务场景和角色路径进行；问题记录同时保留发现阶段标签和统一闭环分类。闭环分类固定为缺陷、需求遗漏、新增优化和后续事项，并逐项给出结论。延期或不纳入本次版本的事项要记录需求方结论。
9. 项目中的即时经验先记入项目记录；确认具有跨项目复用价值后再固化为本 Skill 规则，避免把项目特例写成通用规范。
10. 需求方交互、需求修订、开发者验收和联合验收必须留痕；优先使用飞书云文档和多维表格，`lark-cli` 不可用或无权限时使用 Excel/本地 Markdown 兜底，并保持相同的 ID、状态和分类，不得声称已经同步。
11. 缺少基础产品说明或关键原文时，不得凭空补写功能、页面或验收结论；先列出缺失项并停留在相应阶段。

## 十二步主流程

1. **需求初筛**：需求方简述需求；与开发者首次沟通，判断价值、必要性和基础背景，并记录需求方、主要决策/验收人、本期范围/非范围和验收环境是否已知。
2. **基础产品说明**：需求方主导（必要时开发者协助）说明目的、意义、主要功能及其基本用途、业务角色、基本工作流和主要字段；页面原型可选。需求方需要共同编辑或确认时，将文档放在飞书云文档，工具不可用时使用本地 Markdown/Excel 兜底。
3. **需求对齐会议**：围绕基础说明逐项沟通功能、内部工作流和实现细节；发现矛盾、冲突和缺口，形成会议结论与待定项，并写回共享云文档或兜底文件。此步结束后进入专业化整理，不直接跳过 PRD 开始正式开发。
4. **正式需求文档与 PRD**：开发者将已对齐内容详细拆解；需求文档记录最终需求和来源，PRD 定义产品形态，形成可执行的需求基线。
5. **产品包**：汇总需求文档和 PRD，补充页面 SPEC、每个页面的原型效果图，以及前端、后端的相互依赖执行计划和子任务。产品包首页放版本与追溯索引；控件绑定表按一控件一行建立覆盖关系。对多角色产品补一份轻量的“角色 × 页面/操作 × 数据范围”结论；按项目需要记录安全、隐私、可访问性、浏览器和性能等非功能约束，未决项写明负责人和解除条件。
6. **前端原型开发**：
   - 有合适模板：先建立适配评估，盘点并评估模板的登录、认证、角色/RBAC、导航、基础 UI 和模块边界，标注复用、重做、关闭、风险及安全影响；调整配置并清理无关能力，再按计划构建业务前端。认证与 RBAC 逻辑要保留并验证；视觉不匹配时可重做业务页面，模板整体不适用时记录决策后走无模板分支。
   - 无合适模板：直接按用户指定 UI 风格、页面 SPEC 和产品包构建前端。
   开发中严格执行基线变更规则，避免死控件和无关扩展；前端发现的变更要同步到后端计划。
7. **需求方原型验收**：指定验收人按页面、角色和核心路径确认页面形态、主要交互和核心流程；在共享云文档或多维表格中记录每页、每个角色、每条核心路径的结论、截图/录屏证据及修改建议。
8. **前端返修**：把建议加入计划并修改前端；若改变需求基线，按规则同步所有相关文档和后端计划。重复第 7 步，直到原型意见有明确结论。
9. **后端开发与联调**：按最终产品包实现后端，并与前端联调。以所有绑定控件都有真实数据/API/状态和权限路径为阶段出口；必要时往返修正前端、后端和文档。
10. **开发者自验**：按各业务场景和角色路径验收，优先修复阻断性问题；在多维表格或 Excel 兜底表中记录非阻断问题及处置结论。
11. **验收环境联合测试**：需求方共同测试，记录缺陷、需求遗漏、新增优化和后续事项；开发者逐项修正、复测或提出延期，延期结论由需求方确认并留痕。
12. **完成与沉淀**：确认验收闭环，整理项目经验；开发过程中发现的通用经验可实时进入 Skill 改进候选，最终区分项目特例和通用规则。

## 最小阶段出口

- **G0 初筛**：价值和基础背景足以决定继续或暂缓；需求方、主要决策/验收人、本期范围/非范围和验收环境的缺口已列出。
- **G1 基础说明**：目的、意义、主要功能、角色、基本流程和主要字段齐备；原型可缺省。缺少基础说明正文或关键原文时不得进入 G2/G3。
- **G2 对齐**：会议结论、冲突处理和待定项有记录。
- **G3 开发基线**：需求文档、PRD、页面 SPEC/效果图、前后端计划和追溯索引可用。
- **G4 原型接受**：指定验收人已对每页、每个角色和每条核心路径给出结论并附证据；未通过项已返修并重新验收。
- **G5 联调完成**：绑定控件、数据/API、权限和业务状态贯通。
- **G6 内部验收**：核心场景和角色路径通过，阻断性问题已处理。
- **G7 联合验收**：问题已逐项闭环，或明确记录延期/后续安排。
- **G8 复盘**：项目经验已分类，Skill 改进候选已识别。

## 交互方式

推进时只报告当前阶段、已知结论、阻塞问题、文档/计划变更和下一步。遇到会改变范围、验收、风险或授权的未知信息才向用户提问；其余信息采用明确标注的默认值并记录依据。
