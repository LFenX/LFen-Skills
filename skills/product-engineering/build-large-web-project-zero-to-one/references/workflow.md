# 从 0 到 1 大型 Web 项目工作流

本文件是主流程的执行细节。保持流程轻量：每个阶段只要求能支撑下一阶段的最小产物，不把需求方当成完整系统分析师。

需求文档、会议结论和需求变更优先放在可与需求方共同操作的飞书云文档；开发进度、原型意见、缺陷和验收问题优先放在飞书多维表格。没有 `lark-cli` 或没有权限时，使用 [control-carriers.md](control-carriers.md) 规定的 Excel/本地 Markdown 兜底，并保持编号和状态一致。

## 流程总览

```text
1 初筛 → 2 基础说明 → 3 对齐会议 → 4 需求文档/PRD → 5 产品包
→ 6 前端原型 → 7 原型验收 ⇄ 8 前端返修
→ 9 后端开发与联调 ⇄ 联调修正
→ 10 开发者自验 ⇄ 缺陷修复
→ 11 验收环境联合测试 ⇄ 问题闭环 → 12 总结与 Skill 沉淀
```

不要把第 3 步的会议结论当成完整 PRD，也不要在第 3 步跳过第 4、5 步直接进入正式编码。

## 阶段执行

### 1. 需求初筛

**输入**：需求方的简短描述。

**动作**：

1. 听取业务背景、问题和期望结果。
2. 判断需求是否有真实价值、是否值得投入，以及是否具备继续沟通的基础。
3. 记录明显的背景缺口，但不在本阶段设计完整方案。

**产物**：一段初筛记录，结论为继续、补充信息、暂缓或终止。

**出口**：能够说明“为什么做、为谁做、要改变什么”；需求方、主要决策/验收人、本期范围/非范围和验收环境的缺口已列出。

### 2. 基础产品说明

需求方主导，开发者可协助表达。文档保持基础版本，包含：

- 产品目的和意义；
- 主要功能及每项功能的基本用途；
- 主要业务角色；
- 基本工作流；
- 主要业务字段；
- 页面原型（有则提供，没有不阻塞）。

每项功能写到能让开发者理解其业务作用即可，不要求覆盖所有异常、接口和验收细节。

需求方需要持续补充或确认时，基础说明应作为共享云文档与需求方交互，而不是只在聊天窗口或开发者本地保存一份静态副本。

**出口**：开发者能对产品做出初步整体理解。

缺少基础说明正文或关键原文时，不得进入 G2/G3；先列出缺失项并请求补充，不生成未经依据的功能或页面。

### 3. 需求对齐会议

**动作顺序**：

1. 需求方按基础说明讲解产品、功能和内部工作流。
2. 开发者逐项复述理解，指出矛盾、冲突、缺口和相互依赖。
3. 双方讨论并记录结论、待定项和默认处理方式。
4. 开发者在开始专业化整理前，扫描仓库、现有模板、运行环境和已存在的相关文档。

**产物**：会议结论、冲突处理记录、待定项列表和初始需求基线。

**出口**：口头需求与基础文档不再存在未记录的明显冲突。会后进入 PRD 和产品包准备，不直接跳到正式开发。

### 4. 正式需求文档与 PRD

开发者将基础需求产品化，但维护两个不同职责的文档：

- **需求文档**：保留需求方原始表述、来源、澄清结果、开发者矫正或新增内容，是最终需求依据。
- **PRD**：定义产品形态、产品意义、功能结构、角色、工作流、页面和交互。

“不允许模糊”指不得留下会影响实现或验收、却没有被识别和记录的模糊项。暂不能决定的内容可以标记为待定，并注明负责人或决定条件。

**出口**：每个核心需求有明确表述，且能在 PRD 中找到对应产品表达。多角色产品至少记录角色、页面/操作、数据范围和允许/禁止结果；按项目需要记录安全、隐私、可访问性、浏览器和性能约束，未决项注明负责人或解除条件。

### 5. 产品包与执行计划

产品包至少包含：

- 需求文档；
- PRD；
- 页面 SPEC；
- 每个页面的原型效果图；只有页面确实同构且需求方同意时，才可以复用同一效果图并标注页面变体；
- 前端执行计划；
- 后端执行计划；
- 产品包索引和版本信息。

前后端计划拆成相互关联的子任务，不只按“前端做完、后端再做”写大块任务。对每个交互控件至少写清：唯一控件 ID（`C-xxx`）、需求或页面依据、入口、出口、数据/API/状态来源、权限/角色、前端任务和后端任务；纯展示控件标明数据来源和前端归属。控件绑定表一控件一行；在 G3/G4 前逐页核对按钮、图标、行操作和菜单项，绑定覆盖率必须为 100%。

**出口**：可以沿着“需求 → PRD → 页面/组件 → 前端任务 → 后端任务 → 验收场景”追溯，不存在计划外控件。

### 6. 前端原型开发

先判断是否有合适模板。

**有模板**：

1. 盘点模板已有的登录、角色、导航、聊天、基础 UI 和其他模块。
2. 调整产品名称、角色、导航、配置和视觉基调。
3. 关闭或移除与当前产品无关的模块。
4. 再按产品包开发业务页面。

**无模板**：

1. 提取需求方指定的 UI 风格和视觉约束。
2. 根据页面 SPEC 和效果图构建基础页面壳和业务前端。
3. 不自行增加未授权的功能或组件。

开发过程中发现新事实、需求矫正或新增需求时，先执行“基线变更”流程，再编码：更新需求文档 → 更新 PRD → 更新页面 SPEC/效果图 → 更新前端计划 → 更新后端计划。

### 7–8. 原型验收与返修

需求方按页面、角色和核心路径验收前端原型。每条意见记录在共享云文档或多维表格（无工具时记录在 Excel 兜底表）中，同时填写阶段标签和统一的闭环分类。阶段标签可用“原型不符合”“待讨论事项”等；闭环分类固定为：缺陷、需求遗漏、新增优化、后续事项。未决的“待讨论事项”不得直接标记完成，必须在讨论后映射到一个闭环分类并写明需求方结论。

- 纯视觉或交互修正：更新前端和页面相关计划。
- 改变产品意义、功能范围或数据规则：先更新需求文档和 PRD，再更新产品包及前后端计划。
- 原型未接受时回到第 8 步返修；返修后重新进入第 7 步。

循环出口是需求方对意见有明确结论，而不是“开过一次验收会”。

### 9. 后端开发与联调

开发者按最终产品包实现后端，并与前端联调。联调至少覆盖：

- 页面控件对应的真实数据或 API；
- 角色和数据范围；
- 业务状态变化；
- 成功、失败和空状态；
- 上传、筛选、分页等实际交互。

发现接口、数据模型或状态假设不一致时，往返修正前端、后端、需求文档、PRD 和计划。阶段出口是前端不再依赖未实现的假数据或死控件。

### 10. 开发者自验

按业务场景和角色路径从头走一遍，而不是只检查编译成功。阻断性问题立即修复；非阻断问题记录到多维表格或 Excel 兜底表，标明当前修复、联合验收处理或后续事项，并说明原因。

### 11. 验收环境联合测试

需求方在验收环境测试，开发者在多维表格或 Excel 兜底表维护问题记录。每条问题必须归类：

- 缺陷：原需求已明确但实现错误；
- 需求遗漏：需求文档或 PRD 需要补充；
- 新增优化：原范围外的新想法；
- 后续事项：本版本不处理。

兼容既有 Base 的问题类型时，按以下规则映射：`BUG` → 缺陷；`需求` → 需求遗漏或新增优化（由是否在原需求范围内决定）；`建议` → 新增优化或后续事项（由本次是否处理决定）。原字段可以保留，但不能替代闭环分类。

开发者逐项修正并复测。延期、不纳入当前版本或转为后续事项的结论，需要需求方确认并留痕。涉及需求变化时，先走基线变更流程。

### 12. 完成、复盘与 Skill 改进

确认核心场景、角色路径和需求方验收结论已经闭环后完成本轮交付。记录：

- 做得有效的做法；
- 返工和遗漏的原因；
- 可迁移到其他项目的规则；
- 只适用于本项目的特例。

项目内问题可以即时修正项目文档；只有确认具有跨项目复用价值后，才更新本 Skill。若流程默认止于验收环境，不要擅自执行生产发布。

## 基线变更最小流程

```text
发现新事实/矫正/新增需求
→ 记录原需求、修订内容、原因和影响
→ 更新需求文档
→ 更新 PRD
→ 更新页面 SPEC/效果图
→ 更新前端与后端计划
→ 再实现和验证
```

任何阶段都可以触发该流程，不能只在前端阶段使用。

## 阶段出口速查

| 出口 | 最小判断 |
|---|---|
| G0 | 价值和基础背景足以决定继续或暂缓 |
| G1 | 基础产品说明可供开发者理解 |
| G2 | 会议结论、冲突和待定项有记录 |
| G3 | 产品包和前后端绑定计划可执行 |
| G4 | 指定验收人已对每页、每个角色和每条核心路径给出结论，并附截图/录屏等证据；未通过项已返修并重新验收 |
| G5 | 控件、数据/API、权限和状态已贯通 |
| G6 | 核心场景和角色路径通过内部验收 |
| G7 | 联合验收问题逐项闭环或明确延期 |
| G8 | 复盘完成，Skill 改进候选已分类 |
