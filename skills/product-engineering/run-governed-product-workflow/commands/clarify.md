# clarify

用于消除会改变目标、Scope、Acceptance、风险或授权的未知。

路径：脚本在 `<skill-root>/scripts/`；`<project-root>` 为含 `.project-governance` 的消费项目根，不是 skill 根。

## 1. 先勘察，再提问

VC-PPG-PRO-001 §S1 规定的动作是「检查仓库、文档、环境和 Baseline」，然后才执行 Grill Me。没有勘察结果不得提问，也不得宣称零轮。

按对需求的初步理解定位相关代码，产出结构化勘察结果：

| 项 | 内容 |
|---|---|
| 相关位置 | 涉及的文件、函数、配置、数据结构 |
| 现有实现 | 当前如何工作，包括已有的边界与失败处理 |
| 既有约定 | 命名、分层、错误处理、测试方式等本仓已成立的做法 |
| 分歧点 | 勘察**没能**唯一确定的地方，即候选澄清点 |

分歧点是提问的来源。凭空想出的问题不属于澄清。

## 2. 该问什么

**必须问**，满足任一即问，**与能否自行查出无关**：

- 目标用户、问题、期望行为或完成判定无法表达
- 存在安全、隐私、数据、不可逆、生产影响或 Authority 相关的未知
- 勘察发现多个都合理的实现路径，且选错需要重做
- 会改变外部可见行为，而期望行为未被唯一确定
- 涉及授权、例外或风险接受——这些永远不得由 Agent 推定

**不问**，须全部满足：

- 勘察已给出单义答案（代码、文档或既有约定明确）
- 猜错代价可逆且低，不影响验收结论
- 不触及上面任一条

判据是**猜错的后果**，不是「我能不能查出来」。可发现但选错要重做的，仍然必须问。

问题、推荐默认与随后写入记录的介绍，都使用用户提问所用的语言。

## 3. 怎么问

开场必须先说明本次走哪条路，用用户提问所用的语言，原文写入 `clarification.notice`：

- 零轮：「你的需求已经描述的非常清楚了，并且和项目现状一致，本次跳过向你提问的阶段」
- 提问：「针对你的需求和项目现状，有几个问题需要你先回答，以保证本需求完成的质量」

- 每个问题必须绑定它会改变**目标 / Scope / Acceptance / 风险 / 授权**中的哪一项。绑不上的不问。
- 每轮 3-5 个，各给推荐默认。
- 先给勘察结果，再给问题。
- 用户回复「全部默认」时采用推荐默认并记录 basis。
- High/Critical、不可逆、生产发布、权限扩大、安全/隐私、例外和风险接受必须单独确认，不与其他问题合并。

## 4. 收到回答之后

澄清是循环，不是一次问答。每收到一轮回答，先审回答本身，再回到第 1 节重新判定：

| 回答情况 | `answer_state` | 处理 |
|---|---|---|
| 明确回答了问题 | `Answered` | 记录后继续判定是否还有别的分歧点 |
| 用户回复「默认」 | `DefaultAccepted` | 采用推荐默认并记录 basis |
| 有歧义、与勘察结果冲突、或只回答了一半 | `Ambiguous` | **必须追问**；不得由 Agent 自行选一种解释 |
| 用户明确推迟 | `Deferred` | 记为未决，不得当作已解决 |

回答本身会引入新的分歧点——新范围、新约束、新依赖、与现有实现的冲突——它们是下一轮的提问来源。轮次从 1 连续编号。

## 5. 什么时候可以停

S1 出口条件（VC-PPG-PRO-001 §S1）全部成立才可结束澄清：

- [ ] 目标用户、问题、期望行为和完成判定**可表达**
- [ ] 安全、隐私、数据、不可逆性、生产影响、Authority 和其他阻断 Unknown **已逐项列出**
- [ ] 没有任何回答停留在 `Ambiguous` 或 `Deferred`

三条全部成立才可把 `clarification.state` 写为 `Settled`。**零轮的唯一条件是上述出口条件已成立且有勘察结果支撑。** 不得默认零轮，不得因任务小、用户着急或「看起来很清楚」而跳过。这是本 skill 中零轮规则的唯一表述。

## 6. 归档

澄清点与用户原话同等重要，都是验收基准，必须落到 `before.json`：

| 字段 | 内容 |
|---|---|
| `request_snapshot` | 用户原始提问原文 |
| `clarification.mode` | `Skipped` 或 `Asked` |
| `clarification.notice` | 第 3 节那句话的实际原文 |
| `clarification.survey_refs` | 第 1 节勘察结论的引用，零轮时同样必填 |
| `clarification.rounds[].exchanges[]` | 问题、绑定的变更项、推荐默认、**用户回答原话**、回答状态 |
| `clarification.basis` | 结束澄清或判零轮所依据的勘察结论 |

未归档、未 `Settled`、或仍有 `Ambiguous`/`Deferred` 时，`resolve_tailoring` 从 S2 起返回 blocker，任务进不了二次确认与计划。这是机器强制，不靠自觉。

## 7. 每轮同步第一性原理分析

- Facts：已证实内容。
- Constraints：项目、权限、规范和环境边界。
- Assumptions：可验证但未证实判断。
- Unknowns：来自第 1 节的分歧点，记录 Owner、解除条件和是否阻断。

澄清不是批准。正式 Gate、发布、风险接受和 Authority 仍必须从权威事实源核验。
