# KOC 反馈开发工作流

把飞书反馈记录作为开发任务入口，同时保持 Base 状态、需求共识、代码执行和验证证据一致。

## 强制依赖

- 读取或写入 Base 前，必须加载并遵守 `lark-base`；认证或 scope 问题转 `lark-shared`。
- 需求澄清完成、准备规划时，必须加载并遵守 `run-governed-product-workflow`。不要复制、弱化或绕过它的 Task Profile、Proceed、验证和 Gate 规则。
- 目标 Base、项目路径和字段契约见 [Base 契约](references/base-contract.md)。
- 认领后的阶段、准入和退出条件见 [状态机](references/state-machine.md)。

## 权限边界

- “列出全部/指定类型条目”是只读操作，不产生认领或状态变化。
- 只有用户明确授权探查具体一个或多个条目后，才可认领这些记录。该授权覆盖这些记录的认领字段和本 SOP 后续阶段状态同步，不覆盖其他记录、Base 结构变更、生产发布或无关外部写入。
- Base 缺少必需字段或选项时，停止并请求一次性结构变更授权；不得静默创建字段、选项或修改字段类型。
- 代码执行仍需满足需求共识和 `run-governed-product-workflow` 的人类决定点。认领不等于批准实现方案或发布。
- “值守大模型”仅由人工维护；“生产部署”仅允许用户本人手工维护。Agent 可以读取和展示字段现值，但禁止新增、修改或清空。

## 候选记录不变量

按“唤起开发者”的选项集合做精确判断：

- 值恰好为 `{LFen}`：排除，不列举、不认领、不改写。
- 为空：可选。
- 含任意非 `LFen` 值：可选；`{LFen, Agent}` 也可选。

禁止用字符串“包含 LFen”代替集合判断。用户显式要求覆盖排除规则时，先复述目标记录和影响，再取得单独确认。

## 工作流

### 1. 列举

1. 解析 Base URL 并读取真实表、字段和选项。
2. 按候选记录不变量筛选；用户指定“BUG / 建议 / 需求”或其他真实字段条件时一并下推。
3. 处理全部分页并按序号输出。至少展示：序号、问题类型、重要度、问题描述、提出人、截图可用性、开发状态、开发进度、唤起开发者和回复摘要。
4. 不把列举结果视为已授权任务。

### 2. 认领并开始探查

用户必须点名具体序号或记录并明确授权开始探查。写入前重新读取全部目标；任一目标不符合候选规则、已被他人改写或无法唯一定位时，整批停止，不做部分认领。

认领成功时：

1. 将“开发状态”写为短暂认领态 `开发中`。
2. 将“唤起开发者”精确写为 `LFen + Agent`。
3. 按 Asia/Shanghai 当前时间登记“唤起开发时间”。
4. 回读验证开发状态、唤起开发者和唤起开发时间，再将“开发进度”写为 `澄清需求` 并登记对应阶段时间。

### 3. 澄清需求

- 读取问题描述、回复和全部截图；检查代码、测试、配置和相关产品文档，确认现状、是否存在问题及原描述是否准确。
- 先反馈：对问题的理解、代码证据、描述偏差、未知点和会改变目标/范围/验收的问题。
- 澄清可持续多轮；未达成明确共识前不得修改产品行为。
- 共识达成后，先按 Base 契约追加登记澄清结果，再进入规划。
- 若问题不存在、无法复现或描述不成立，保持 `澄清需求`，登记事实并请用户决定处置；不得自行标记完成。

### 4. 规划、执行与闭环

除进入完成终态外，保持“开发状态”为 `开发中`，严格按 [状态机](references/state-machine.md) 同步“开发进度”：

`规划中 → 执行中 → 复核中 ↔ 返修中 → 已完成`

- 进入 `规划中` 后调用 `run-governed-product-workflow` 建立或更新受控任务并制定计划。
- 获得该流程要求的 Proceed 后才进入 `执行中` 并修改代码。
- 实现和必要验证结束后进入 `复核中`，检查需求覆盖、代码、测试、权限、审计、文档、构建与项目 `update_log/`。
- 发现问题则进入 `返修中`；返修完成回到 `复核中`，直到没有未关闭问题。
- 只有验收标准有证据支持且复核无未解决项时，才能在同一次记录更新中将“开发进度”和“开发状态”均写为 `已完成`，并回读验证两项。
- 修复完成后，部署并重启服务。该动作仅在用户已明确授权本次部署时执行；未获得部署授权不得自行部署。部署前后必须核对本项目进程、监听端口和健康检查，禁止影响其他项目服务。

## 同步与停止规则

- 每个阶段开始前先写入对应“开发进度”和阶段时间，写后回读。“开发状态”使用 `待开发 / 开发中 / 已完成`：中间研发阶段保持 `开发中`；当“开发进度”写为 `已完成` 时，必须在同一次记录更新中同步将“开发状态”写为 `已完成`，并回读验证两项。同步失败时停止该阶段，避免 Base 与代码事实分叉。
- 多条记录默认独立推进、独立登记。只有变更面确实不可分且用户同意时，才共用一个 `run-governed-product-workflow` 任务；Base 中仍逐条维护状态和结论。
- “生产部署”对 Agent 只读，禁止新增、修改或清空；`已完成` 仅表示开发与复核闭环，不代表已上线。
- 不覆盖已有回复；按 Base 契约追加带时间的结构化记录。
- 任何目标变化、范围变化、验收变化或新证据，先回到相应澄清/规划 Gate，再继续执行。
