# 状态机

## 状态与 Gate

| 阶段 | 开发状态 | 写入“开发进度” | 核心动作 | 退出条件 |
| --- | --- | --- | --- | --- |
| 候选 | `待开发` | 不写入 | 列举符合候选规则的记录 | 用户点名记录并明确授权探查 |
| 认领 | 写为 `开发中` | 不写入 | 同步 `LFen + Agent` 和唤起开发时间 | 开发状态、路由和时间均验证成功 |
| 需求澄清 | 保持 `开发中` | `澄清需求` | 理解描述、检查截图与代码、验证现状、持续提问 | 用户与 Agent 对问题、范围和验收达成明确共识，且澄清结果已登记 |
| 规划 | 保持 `开发中` | `规划中` | 加载 `run-governed-product-workflow`，按其路由建立任务、应用第一性原理并制定计划 | 计划满足治理要求并取得所需 Proceed |
| 执行 | 保持 `开发中` | `执行中` | 按批准范围修改代码、测试和文档，维护治理证据与项目日志 | 实现完成且执行阶段验证达到进入复核的条件 |
| 复核 | 保持 `开发中` | `复核中` | Review 需求覆盖、实现、回归、构建、权限、审计、文档和证据 | 无未关闭问题则完成；有问题则返修 |
| 返修 | 保持 `开发中` | `返修中` | 修复复核发现的问题并重跑受影响验证 | 返修完成，进度回到 `复核中` |
| 完成 | 写为 `已完成` | `已完成` | 在同一次记录更新中写回两项终态并回读验证 | 所有验收有证据、复核无未解决项，且两字段均验证为 `已完成` |

## 转移规则

```text
开发状态：待开发 → 开发中 → 已完成
开发进度：澄清需求 → 规划中 → 执行中 → 复核中 → 已完成
                                      ↑         ↓
                                      └─ 返修中 ┘
```

- 每次进入阶段前先同步 Base 的“开发进度”和对应阶段时间，写后回读；同步失败时不得开展该阶段的物质动作。进入完成终态时必须在同一次记录更新中同步写入 `开发进度=已完成` 和 `开发状态=已完成`。
- `开发状态=开发中` 是完成前的认领锁定态，不替代“开发进度”。认领验证后立即写入 `开发进度=澄清需求`；完成写入后回读两字段，任一字段不是 `已完成` 都不得视为完成。
- 需求澄清允许多轮，等待用户回复时保持 `澄清需求`。
- 规划与执行受 `run-governed-product-workflow` 的 Minimal/完整载体判定、Proceed、Amendment 和 Gate 约束。
- 新证据改变问题、范围、验收或方案时，停止受影响动作并回到 `澄清需求` 或 `规划中`。
- Review 必须发生在 `开发进度=复核中`。Review 发现的问题不能在原进度静默修补，先写为 `返修中`；修复后必须再次进入 `复核中`。
- `已完成` 不等于 `生产部署=已上线`。“生产部署”仅允许用户本人手工维护；Agent 可以读取和展示，但禁止新增、修改或清空其值。

## 非正常分支

- 问题不存在、无法复现、描述不准确或证据冲突：保持 `澄清需求`，登记事实，请用户决定关闭、改写或继续调查。
- 关键输入缺失：保持当前状态并列出解除条件，不猜测结论。
- 用户暂停：保持当前阶段，不自动回退或完成。
- 用户撤销任务：记录决定，但不得自行选择未定义终态；询问用户要写入哪个现有状态。
- Base 写入部分成功或验证失败：停止代码动作，报告每条记录的实际值；修复一致性后再继续。

## 多条记录

- 每条 Base 记录独立满足状态准入和退出条件。
- 一项完成不得带动同批其他记录完成。
- 多条记录共用一个代码变更时，分别登记澄清结论和验证证据；任何一条未通过验收时，该条不得写为 `已完成`。
